# Соответствие варианту 1 и общим требованиям

Здесь «реализовано» означает наличие правил и структур в проекте. Корректность проверяется `make check` и дополнительными тестами. Не все возможные программы могут быть исчерпывающе протестированы.

| Правило задания | Реализация | Проверка |
|---|---|---|
| `source: sourceItem*` | `source`, `function_list` | `test-spec`: пустой файл, прототипы; `check.sh`: запрет глобальных переменных |
| `typeRef` (встроенный / пользовательский / массив) | `base_type`, `type_ref` | `test-spec`: встроенные, пользовательские и массивы |
| `funcSignature`, `argDef` | `function_def`, `parameter_items`, `parameter` | `test-spec`: прототипы, необязательные типы, списки |
| `statement.var` | `declaration`, `variable_list`, `variable` | `test-spec`: несколько переменных, инициализация |
| `statement.if`, `else` | `if_statement`, AST_IF | `test-spec`: ближайший `else`, `test_parser.c` |
| `statement.block` | `block`, `statement_list` | `test-spec`: пустые и вложенные блоки |
| `statement.while`, `do`, `break` | соответствующие PEG-правила и AST | `test-spec`: оба цикла и break |
| `statement.expression` | `expression_statement` | `test-spec`: выражения и вызовы |

| `expr.place`, `literal` | `identifier`, `literal` | `test-spec`: идентификаторы и литералы |

## Принятые решения и ограничения

1. PackCC генерирует C-парсер из `.peg`, отдельный Flex не требуется.
2. Тексты литералов сохраняем в AST как исходные строки: вычисления — не часть задания №1.
3. Набор и приоритеты операторов дополняют недоопределённые `binOp`/`unOp` из задания. Присваивание правоассоциативно; арифметика обычно левоассоциативна.
4. `return` в исходном варианте не присутствует. Мы не добавляем оператор самостоятельно.
5. Исходное правило `typeRef` допускает `int[,]`, хотя для выражений по заданию требуется лишь поддержка одномерных массивов.
6. Восстановление после нескольких синтаксических ошибок не реализовано. В интерфейсе всё равно используется коллекция диагностики, пригодная для расширения.
7. Отказ при выделении AST-узла обнаруживается. **Отказы выделения памяти внутри сгенерированного PackCC пока не имеют доказанного безопасного восстановления**: обработчики PackCC по умолчанию используют `exit(1)`. Это открытый пункт общих требований; стандартные тесты и обычный Valgrind не закрывают его.
8. AST не проверяет семантику программы (типы переменных, наличие определения функции, `break` вне цикла); это выходит за пределы синтаксического анализа.
