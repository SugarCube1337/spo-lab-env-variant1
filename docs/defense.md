# Шпаргалка для защиты задания №1

## 1. Как показать работу программы за 5 минут

Из корня проекта в WSL:

```bash
make clean && make
make check
make demo
make demo-errors
```

Открой **`build/linux/demo/01-priority.dot`** через расширение Graphviz Interactive Preview.
Затем открой **`02-parentheses.dot`** и сравни корни выражений.
Остальные примеры — в `examples/defense/valid/`, готовые SVG — в `build/linux/demo/`.

### Пример 1: приоритет `*` над `+`

```c
main() { int x = 2 + 3 * 4; }
```

Ожидаемая часть AST:

```text
Binary +
├── Integer 2
└── Binary *
    ├── Integer 3
    └── Integer 4
```

**Что сказать:** правило `additive` использует `multiplicative`, поэтому `3 * 4` стало вложенным выражением, а сложение — внешним. Парсер не считает результат `14`, он только строит дерево.

### Пример 2: скобки меняют структуру

```c
main() { int x = (2 + 3) * 4; }
```

```text
Binary *
├── Binary +
│   ├── Integer 2
│   └── Integer 3
└── Integer 4
```

**Что сказать:** в правиле `primary` скобки вызывают разбор полного `expression`; результат становится одним поддеревом. На AST скобки отдельным узлом не хранятся — сохраняется их влияние на группировку.

### Пример 3: ассоциативность

`10 - 3 - 2` группируется как `(10 - 3) - 2` — слева вложен ещё один `Binary -`. Правило `additive` использует левую рекурсию.

`a = b = c = 1` группируется как `a = (b = (c = 1))` — справа вложен `Binary =`. Правило `assignment` рекурсивно справа.

### Пример 4: логика

`a || b && c` имеет корень `Binary ||`; правый потомок — `Binary &&`. Логическое И сильнее ИЛИ в нашей спецификации.

### Пример 5: вложенный `if`

`else` относится к ближайшему внутреннему `if`. Посмотри `06-nearest-else.dot`: у внешнего `AST_IF` ветви `else` нет. Это покрыто отдельным тестом AST.

### Пример 6: функции, массивы, циклы

- `07-loops.dot` — узлы `While`, `If`, `Break`, `DoWhile`.
- `08-functions-arrays.dot` — объявление `sum`, тип `int[]`, вызов `sum(1, 2*3)` и индексация `values[0]`.
- `09-literals.dot` — `Hex`, `Bits`, `Bool`, `Char`, `String`.
- `10-empty.dot` — один корневой узел `Program`, потому что `sourceItem*` допускает ноль функций.

### Пример преподавателя с тремя присваиваниями

Выполни `make teacher`: появятся 4 монохромных дерева в `build/linux/teacher/`.
В `docs/teacher.md` приведена точная вложенность `a + b*c + d`, `a*b + c*d` и `z + 4 = f(1,2,3) = 3`.
Форма дерева проверяется автоматически тестом `tests/test_teacher.c` при `make check`.

## 3. Что выполняется при запуске

1. `main.c` читает файл **блоками** в динамический буфер.
2. `parse_source_n()` в `parser.c` вызывает сгенерированный PackCC-парсер.
3. Правила `language.peg` распознают конструкции и через `ast_make()` создают узлы AST.
4. `ParseResult` содержит статус, корень дерева и коллекцию сообщений об ошибках.
5. При успехе `ast_write_dot()` записывает DOT; по нему Graphviz делает SVG.
6. `parse_result_free()` освобождает память дерева и диагностик.

**Важно:** парсер не исполняет программу и не проверяет семантику (например, объявлена ли переменная). Оператор `return` отсутствует в выданной грамматике и нами не добавлен.

## 4. Как показать отладчик и память

В `src/main.c` поставь breakpoint **на строке после** `result = parse_source_n(source, length);`.
Открой пример `examples/basic.spo`, нажми F5. В Watch введи `result.root` и раскрой потомков; `.vscode/ast.natvis` показывает подписи для `AstNode`.

Проверка Valgrind: `make memcheck`. Скажи: «Я проверил освобождение памяти и на корректном, и на ошибочном вводе» **только если команда действительно прошла**.

## 5. Типичные вопросы и короткие ответы

**Почему PackCC?** Он генерирует C-парсер по PEG-спецификации. Грамматика описана отдельно от основного C API.

**Что такое PEG?** Это грамматика с упорядоченным выбором альтернатив. Парсер пробует варианты в заданном порядке; PackCC использует мемоизацию и поддерживает левую рекурсию.

**Чем AST отличается от текста?** AST хранит связи между конструкциями; например, `*` становится потомком `+` при `2 + 3 * 4`.

**Зачем `AST_LIST`?** Чтобы хранить произвольное количество функций, операторов, параметров и аргументов. На графе технические узлы списка скрыты, но в памяти они существуют.

**Что при ошибке `int x = ;`?** Парсер возвращает ошибочный статус и диагностику с позицией. Только CLI печатает её в `stderr`; модуль разбора ничего не печатает.

**Почему пустой файл корректен?** По исходному `source: sourceItem*` список функций может содержать ноль элементов.

**Какие ограничения остались?** Полноценное восстановление после нескольких ошибок не реализовано; безопасное восстановление после отказов выделения памяти **внутри самого PackCC** ещё не подтверждено. Это важно не скрывать.
